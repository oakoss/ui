# Registry

How to add or change items in `packages/ui/registry.json`. Each entry is a rule and its reason.

- **Dependencies are written `oakoss/ui/<name>`, with no ref.** That address installs from `main` on GitHub, and the docs build rewrites it to the same release's folder (`/v<version>/r/<name>.json`, or `/r/` for the latest), since shadcn resolves each dependency by its own address and a ref on the named item doesn't carry to them. So every install from the site stays on one release. `registry-release.test.ts` checks that each release folder's items and index depend only on items in that folder.
- **Every `registry:ui` item depends on `oakoss/ui/theme`,** which installs the tokens and the React Aria Tailwind plugin the variants need.
- **Each theme family is a generated `theme-<family>` item that carries only colors and depends on `oakoss/ui/theme`.** shadcn installs the dependency first and the family's values win, so style and type tokens stay in one item. Measured on shadcn 4.21.4: shadcn overwrites existing cssVars only when a requested item (not a dependency) is a theme, so `add <component>` keeps an installed family, while `add theme` or `add base` resets it. The generator owns every `registry:theme` item except `theme`: it rewrites each family's `theme-<family>` item and refuses any other, so don't hand-write one, and delete a removed family's item by hand. `theme-items.test.ts` checks each family item overrides every color the theme sets, with the values of its `themes.css` block.
- **The `themes` item ships `themes.css` as a `registry:file` inside a `registry:item`, with an `@import` in its `css`.** Measured on shadcn 4.21.4: other file types go through shadcn's transformers, which drop a file's leading comments and with them the palette credits. shadcn writes the import exactly as given, after the project's last `@import` and once however often the item is added, comparing the exact text, so the same import in the other quotes gets added again. The import is relative to the project's stylesheet while the target is rewritten on its own (`src/` dropped when the project has none), so the path is right from Vite's `src/index.css` and breaks the build from Next's `app/globals.css` or React Router's `app/app.css`; the installation page says how to fix it. A theme's `cssVars` land in `:root` and `.dark` after every import, which is why `themes.css` selectors repeat an attribute. Like components, it installs as `@oakoss/themes`; the docs site's `/r/themes/` folder holds the theme panel's items instead, built with the site and depending on `/r/theme.json`. `theme-items.test.ts` checks the item.
- **Project setup goes in the `base` item, and its `config` sets only `iconLibrary`.** Only `shadcn init` writes a base item's `config`; `shadcn add` ignores it. The docs build adds the `@oakoss` registry to each built `base`'s config, pointing at its own folder, so `init https://ui.oakoss.dev/r/base.json` sets up the namespace too. Existing projects add the namespace to `components.json` by hand and run `add @oakoss/base`, keeping the icon library their `components.json` already names. `extends: "none"` keeps `init` from also installing shadcn's own style.
- **CSS a theme's `cssVars` can't carry goes in the base item's `css`** (`color-scheme`, the reduced-motion layer). `registry.test.ts` checks the reduced-motion layer against `src/styles/base.css` and `color-scheme` against `src/styles/theme.css`.
- **CSS a component needs that classes can't express ships with its item and lives in `src/styles/<item>.css`.** Progress's indeterminate keyframes and its `--animate-*` variable are the item's `css` and `cssVars.theme`, which shadcn writes into the project's `@theme inline` (measured on shadcn 4.21.4: re-adding the item doesn't duplicate them), so installing another component never pulls them in. A custom variant goes in the item's `css` too: Table's `linked:` names the `aria-current` selector its classes repeat, and shadcn writes it at the top level of the project's stylesheet, once however often the item is added (measured on shadcn 4.21.4). Storybook and the docs load the same CSS through `globals.css`, and `registry.test.ts` checks the item against its file and the import. Component styles stay in `tv` classes otherwise; this is for keyframes and variants.
- **A forked item names its source in `meta.upstream`** (`shadcn-ui/ui@<commit>:<path>`), so diffing upstream from that commit finds fixes to port. `meta` stays in the registry and never reaches the installed files; `registry.test.ts` checks the format.
- **Docs demos aren't registry items.** An item per demo buries the components in `shadcn search`, and forces a demo's packages (a router, a form library) on whoever installs it. Multi-component compositions get curated as `registry:block` items after every component is ported.
- **A dependency whose next major breaks the item pins its major** (`@tanstack/react-table@^9`): shadcn installs the latest release, and v9 already broke v8's API. Stable packages stay unpinned, like `react-aria-components`. `registry.test.ts` reads the name before the range.
- **An item ships what it imports:** every local file in its `files` or through `registryDependencies`, and every package in `dependencies`. `registry.test.ts` checks both.
- **No two files in the registry share a name,** whatever their folders or extensions. Measured on shadcn 4.21.4: it rewrites each import to a file the same `add` installs by name, so with `lib/toast/toast.ts` beside `ui/feedback/toast/toast.tsx` the component's import of the store became an import of itself, and the install failed to typecheck. Unrelated items named in one command (`add a b`) clash the same way; separate adds don't. That's why the toast store's entry point is `toast-api.ts`. `registry.test.ts` checks it.
