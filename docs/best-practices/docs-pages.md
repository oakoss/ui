# Docs pages

How to write a component page in `apps/docs/content/docs/components`. Each entry is a rule and its reason. `button.mdx` is the reference page.

- **A new page goes in a sidebar group** in `content/docs/components/meta.json`, under the heading that names what it's for (Buttons, Inputs, Choices, Date and time, Menus, Overlays, Navigation, Layout, Data display, Feedback). Groups follow what a reader is looking for, not the package folder a component installs into. A page the list leaves out drops from the sidebar, and the prerender never builds it, since it finds pages by their links; `sidebar.test.ts` fails until the page is placed.
- **Sections in this order:** a preview, then `## Installation`, `## Usage`, `## Examples`, `## Accessibility` and `## API`. Visitors and agents find the same thing in the same place on every page; `build.test.ts` checks the order.
- **Front matter names the registry item and the React Aria page** (`item: button`, `reactAria: https://react-aria.adobe.com/Button`). The links under the title come from them: Source (the item's component file on GitHub) and React Aria.
- **The preview is `<ComponentPreview name="<demo>">`** wrapping the demo from `src/components/demos`. A remark plugin turns it into Preview/Code tabs at build time. The Code tab loads the demo file's highlighted source as its own module when opened (`demo-sources-plugin.ts`), since inlining every demo pushed the Data Table page's chunk past `bundle.test.ts`'s 400 kB limit; the `.md` and `llms-full.txt` output show the code inline (search indexes no code blocks). Demos draw no border of their own; the preview frame does.
- **Installation is `<ComponentInstall item="<name>" />`.** The plugin builds the CLI command and the manual steps (packages, then every file the item and its registry dependencies install, then any CSS a component item ships, such as Table's `linked:` variant) from `packages/ui/registry.json`, so they can't drift from what `shadcn add` installs. The page shows each file's source; the `.md` and `llms-full.txt` output list the files with GitHub links instead, since the shared files would otherwise repeat on every page. The Manual tab starts loading all of its files at once (`ManualSources`): React renders a lazy sibling only after the one before it loads (its pre-warm loses the race when chunks resolve quickly), so the Data Table page's 49 files arrived one by one, and the tab took 1.7s, or 10.1s on a 6× slower CPU, against 0.8s and 3.8s now. Package-manager tabs remember the visitor's choice across pages.
- **Every example is live:** one sentence naming the prop it shows, then a `<ComponentPreview>` of its own demo (`src/components/demos/<component>-<example>.tsx`). The Code tab shows that file, so the code a visitor copies is the code that rendered. Demos are self-contained: one that needs state (form errors, a pending flag) keeps it locally. A heading in the top preview, under the page's `h1`, is level 2 (`headingLevel`, `level`), or axe's heading-order fails on the built page.
- **Accessibility says what React Aria provides, what the component adds, and the keys.** Take keyboard behavior and data attributes from React Aria's source or docs, not memory. Link the WAI-ARIA pattern where one exists. Say "React Aria adds no keys" when the native element's behavior stands.
- **API is one block per part:** `### <Part>`, a line naming what it extends with a link, then `#### Props` (own props only, via `auto-type-table`, then "Also accepts…"; the `.md` and `llms-full.txt` output get the same props as a Markdown table), `#### Data attributes` and `#### CSS variables` as hand-written tables. Parts with no props of their own share one table.
- **A demo that reads the visitor's clock renders inside `<ClientOnly>`** (`src/components/client-only.tsx`), with a fallback of its height at each pointer size and wrap (the range demo's fallback wraps like its months), in the page rather than the demo file, so the Code tab stays the code a visitor copies; the `.md` and `llms-full.txt` output drop the wrapper (`expansion-output.ts`). Pages are prerendered at build time, so a calendar opened on a later day disagreed with the browser: React threw hydration error #418 on the Calendar page.
- **A page built from package data reads it through a data module,** such as `virtual:token-reference` (`data-module-plugin.ts`), never by importing the package in a component: `bundle.test.ts` fails if token code reaches the browser. Its remark plugin records the same data as Markdown with `recordMarkdown`, so the `.md` and `llms-full.txt` output get a table while the page keeps its interactive one. Keep that data compact, with entries in row order and each string stored once: the token reference took 211 kB with every entry keyed by name and 82 kB that way, against `bundle.test.ts`'s 400 kB chunk limit. The page and the remark plugin throw on a missing entry rather than render a blank cell.
- **Landmarks on a page have distinct names,** since axe runs every rule on every built page, at desktop and phone widths. Two demos of the same landmark component on one page (Breadcrumb, Pagination, a Data Table's region) each pass their own label. Fumadocs' code blocks and tables go through `CodePre` and `ProseTable`, which follow `useScrollRegion`: Fumadocs makes every code block a region, which put an unnamed landmark on each block and failed `landmark-unique`.
- **A demo that renders an icon needs an `IconResolverContext` provider,** as Storybook's preview has. Resolve only the names `icons.tsx` uses rather than importing a library's namespace, which would ship every icon to the site.
