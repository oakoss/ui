# Testing

How to write stories and tests. Each entry is a rule and its reason.

- **Stories are the component tests.** Assert behavior (accessible name and description, computed styles) rather than class names, and check a guard by breaking the code under it: a test that passes either way isn't guarding anything.
- **Stories and demos use our components.** A component inside a button or link sits in our `Button` or React Aria's `Link`, and buttons that only drive a story's state are our `Button` too. Stories then exercise what consumers write, such as Button's label wrapper, pending state and focus ring, which a plain element skips. Plain elements stay only where they're the point: an inline link in text, a demo of wrapping a non-React-Aria element (`Focusable`), or a test that needs a native focus target or submit button.
- **A generic component's stories use a pinned alias.** Storybook can't read a generic component's props, so `const SingleSlider = Slider<number>` is the meta's `component`, and `StoryObj<typeof meta>` types the args. An untyped decorator in that meta turns every story's args into `never`, so size the component through `args` (`className: 'w-80'`) instead.
- **Type rules get type tests.** `@ts-expect-error` cases in a `*.test.ts` fail the typecheck when a rule stops holding.
- **Tests and stories import another folder's source through their package's `#/` aliases**, not `../`: a docs test imports `#/lib/site`, and a story imports Storybook's shared helpers as `#/helpers/parts` or `#/helpers/paint`. Moving the file then doesn't break its imports.
- **Story helpers shared across categories live in `apps/storybook/src/helpers/`;** one that serves a single category, such as `overlays/overlay-test.ts`, sits beside its stories. Neither goes at the top of `src/`, beside the category folders.
- **Stories run axe in the light and dark projects** (stories tagged `forced-colors` run only in their own projects, under Windows High Contrast emulation), and RTL stories set `globals: { locale: 'ar-EG' }`.
- **Forced-colors stories run under the light and the dark High Contrast palette** (`forced-colors` and `forced-colors-dark`). Chromium picks the palette from the context's color scheme, which changes most system colors (Canvas turns black, Highlight cyan, LinkText yellow; Mark and MarkText stay), so compare against system colors or a native control rather than fixed values. `Internal/Forced colors` checks each project got its palette, and that the body paints Canvas, which `contrast` and `flatBackground` paint over.
- **Storybook's Docs pages follow the theme toolbar through `ThemedDocsContainer`** (`apps/storybook/.storybook/preview.tsx`), which hands Storybook its own dark or light theme, and `app.css` gives each story frame `--color-background` and `--color-foreground`. Storybook paints the page and frames in its own theme, light by default, so the dark theme's text read near-white on white; its theme parses only hex, rgb and hsl, so our oklch tokens reach the frames through CSS. Vitest never renders a Docs page: `Internal/Docs frame` pins the CSS rule, and the container is checked by eye.
- **Docs e2e runs axe on every prerendered page, light and dark** (`apps/docs/e2e/a11y.spec.ts`), for the page-level rules a story can't see: heading order, landmarks, the site's own colors. A rule switched off there is listed in the spec with its reason and a bead; WCAG rules stay on.
- **Check what forced colors paint with `paintedColor`** (`apps/storybook/src/helpers/paint.ts`), which screenshots an element and returns its dominant color. Computed styles don't show the backplate behind text, so a label covered by it still reads HighlightText there. Compare against a color the failure would match, such as the page's, so the check fails without the fix; comparing a label to its own tight-fitting control passed either way.
- **Screenshot only text a backplate could cover, once per check.** An element with `forced-color-adjust: none` paints its computed colors, so read those, and check that opt-out to rule out a backplate: Table's linked and selected cells kept their system-color backgrounds without it, so a cell-sized screenshot passed while their text sat on the page color. Compare a screenshot with `flatBackground` (`apps/storybook/src/helpers/color.ts`), an element's computed background painted over the page, rather than with a second screenshot. Screenshots stalled past the test timeout when Vitest 5.0.3 ran too many pages at once.
- **Compare translucent tints after flattening each onto the page.** `contrast(top, bottom)` draws the first color over the second, so a half-transparent stripe over the solid hover color read as that color, 1.0. Paint each tint over the page on its own canvas and compare the opaque results, as Table's `TintsDistinct` story does.
- **Compare forced-colors output against a native control** rendered in the same story, such as `<button disabled>` for a disabled Button, rather than hardcoded system colors, which differ between the light and dark palettes. Matching a native disabled button caught a disabled link-button's black text and a disabled Button's half-faded gray. Check a part's element itself, not its label: a Button's inner span reported full opacity while the button was faded.
- **Every forced-colors class has a story that fails without it,** or it goes. Removing each in turn found 27 that failed nothing: most changed a disabled, selected or focused state no story rendered, such as a disabled checkbox's GrayText border, and one hid a bug, an invalid Calendar day's white text on Mark. Render combined states too: checked and disabled, Checkbox, Radio and Switch drew Highlight, since the selected color came later than the disabled one, so they read as enabled. One class did nothing in any browser (a `bg-none` already set outside forced colors) and was removed; a Highlight border over a Highlight fill isn't a no-op, since Chromium's emulated Highlight is translucent and the two layers draw a darker edge. Where a native control or system color is the reference, compare with `computedColor('GrayText')` and the like, which resolve in each palette. Some can't fail in Chromium and stay: `border-[ButtonText]` on Checkbox, Radio, Switch and Slider, since Chromium's emulated palettes draw forced borders in CanvasText, which equals ButtonText in both; and NumberField's disabled stepper `text-[GrayText]`, which Chromium already gives a disabled `<button>`. They match native controls on Windows themes and browsers where those differ.
- **`CssCheck` stories assert values from utilities used only in `packages/ui`,** so they fail if Tailwind stops scanning the package. Keep those class names out of every Storybook file, comments and `toHaveClass` checks included: Tailwind scans the app's own files as text, so naming a utility generates it. TextField's and Dialog's checks passed without the package scanned because one story's comment named its utility and another story used it. Confirm a new check by removing `@source '..'` from `packages/ui/src/styles/globals.css`.
- **Test state styles by setting React Aria's state attributes.** `hover:` and `pressed:` match `data-hovered` and `data-pressed` on React Aria elements, so set those and read the style. Simulated pointer events don't reliably reach that state on CI: hovers got lost or stuck while the same stories passed locally. Set every state explicitly, the resting read included, since a stuck hover leaves `data-hovered` set; for the resting read, delete the attribute, since the variants match it at any value, `"false"` included. This doesn't check that real pointer events reach the element, so a change that blocks them (`pointer-events-none`) goes uncaught. A story whose element has a hover style worth checking ends with `data-hovered` set, so axe checks that state every run.
- **Check that an overlay stayed open with `stayedOpen`,** which waits past the exit transition and checks the overlay is still mounted without `data-exiting`. A settled overlay stays visible and findable by role while it closes, so `toBeVisible` and a fresh `getByRole` both pass on one that's closing: Sheet's `NotDismissable` did.
- **Read where an overlay enters from by setting `data-entering` or `data-exiting` on the settled panel,** with `inState` from `apps/storybook/src/overlays/overlay-test.ts`. By the time a story can measure, the real entering state has ended. Measure a panel after `settled`, which waits for its entering state to end and then jumps every finite animation on the page to its end rather than waiting them out. It finishes the whole page, not just the panel, because a check can depend on another element's transition: finishing only the panel left a trigger's pressed-scale transition unstarted, and a DropdownMenu gap check passed with Button's scale exception removed.
- **Open an overlay inside a Dialog only after the dialog's panel has `settled`.** A popover places itself against its trigger once, so one opened while the dialog was still scaling in sat 6.5px below the trigger instead of 8, and 1px apart between two container runs. A story about an overlay open as the dialog opens settles both, then dispatches a window `resize`, which makes React Aria place it again.
- **The Visual workflow screenshots every story where its play function ends** (`.github/workflows/visual.yml`, with `captureStory` from `apps/storybook/src/helpers/visual.ts`), and comments on a PR with the images that changed since the nearest `main` capture at or before its merge base, past 50 differing pixels; the run's summary links a `visual-changes` artifact with only those images (diff, PR and `main` for each change, plus new and deleted ones). It runs only for changes that can alter a screenshot (the workflow's `paths`, stories and demos included), on `main` as on PRs, so a commit outside them has no capture of its own. A story whose final state depends on timing shows up as a change on unrelated PRs. Motion driven from script escapes the screenshot's animation pause: Embla left carousels a fraction of a pixel short of rest, about 1,000 changed pixels per story in 7 to 11 of 60 images between identical runs on macOS, so `captureStory` waits for a carousel's transforms to hold for 400ms (0 of 60 after), and fails the story if one is still moving after 3s. Embla's last 0.01px step can come about 350ms after the one before it. New or renamed stories show as added or removed.
- **Hover stories start with `hoverFresh` and end with `leave`,** from `overlay-test.ts`. React Aria opens a tooltip or hover card on hover only once its interaction modality is `pointer`, which a `pointerenter` doesn't set; `hoverFresh` calls `setInteractionModality('pointer')` before hovering, where clicking the page first lost hovers on CI. Tooltips and hover cards share one warm-up, set by a hover (even one a controlled trigger ignores) and by keyboard focus (even on a disabled trigger). It cools down 500ms (or the close delay, if longer) after a close is requested, and never when a story unmounts. So `leave` unhovers, which requests that close, `hoverFresh` waits out the cooldown, and a story that focused a trigger moves focus off it before `leave`.
- **Hover an overlay that opens at once with `hoverAt`,** which puts the pointer on the element's center. `userEvent.hover` reports every pointer event at (0,0). An overlay opening on a delay is still closed when its `pointermove` arrives, but one opening at once (warm, or hovered again while closing) is open, and React Aria closes it because (0,0) is outside its safe area. That hid a tooltip and hover card left mounted after disabling.
- **Check delays as lower bounds, not fixed instants.** Assert closed right after the hover, then wait with `slowTimeout` inside `expectAfter`, which checks at least the delay passed: for opening, until the overlay appears; for closing, until `exitStarted`, since removal waits for the exit transition too. A busy CI runner stretches time, so `wait(300)` against a 500ms delay flakes, and an upper bound fails the same way. Test a consumer's delay with one longer than the default, not 0, so a dropped prop or a leftover warm-up opens too soon and fails rather than passing. A `wait` before checking that nothing opened is safe: a slow runner can't make it fail.
- **Every story starts with the real pointer off-screen,** parked by `parkPointer` (`apps/storybook/src/helpers/pointer.ts`) in the preview's `beforeEach`. Vitest's browser clicks move the real mouse, and Chromium hovers whatever renders under where it stopped, so Textarea's forced-colors story read a hovered border in about one CI run in four. Parking at the page's (0,0) isn't enough: Vitest runs have no Storybook padding, so that hovered each story's top-left element.
- **CI runs story files one at a time, one theme project after another** (`fileParallelism` and `sequence.groupOrder` in `apps/storybook/vitest.config.ts`). Running them in parallel on the shared runner starved the timers of hover cards that never opened. To keep that and still finish sooner, CI splits the suite across two `storybook` jobs on their own runners (`vitest --shard`), each running its share one file at a time; locally, the two shards took 144s and 149s against 282s for the whole suite in CI mode. Local runs take half the cores (`maxWorkers: '50%'`, which caps the pages all projects share): `pnpm test` runs the docs build and its browser tests at the same time, and with Vitest's default of all but one core, full runs on a 12-core Mac timed out docs pages and failed story imports that passed alone. Capped, two uncached full runs passed in 232s and 226s, and the suite alone took 77s, against 88s with the default. A failing story prints its console output (`silent: 'passed-only'`).
- **CI retries a failed story or docs end-to-end test once; one that passes only on retry is a bug.** A story shows under "Flaky Tests" in the job summary, from Vitest's GitHub Actions reporter, and a docs test in Playwright's "Run Summary" notice. Fix it, or skip it with a link to an issue tracking it. Never raise the retry count to hide one, and never set `retry` in a story or test file, where it would hide that file's own flakiness.
- **Drive state changes from the play function, not timers set at mount.** A component that disables itself 1000ms after mounting races the runner; store a setter the play function calls once it has seen the state it needs.
- **Finish transitions after changing state, before reading styles.** `getComputedStyle` returns a running transition's current value, which right after a class switch is the old one.
- **Run the docs tests through turbo** (`pnpm turbo run test --filter=@oakoss/docs`, or `pnpm test` for every package), not the package script. Both docs suites read `apps/docs/dist` (the Vitest checks read its files, and e2e serves it), and only turbo's `test` task builds it first (`apps/docs/turbo.json`); `pnpm --filter @oakoss/docs test` ran against a stale build and passed while the site's build was failing.
- **CI restores one pnpm store per lockfile and saves it only from `main`** (`.github/actions/setup`), pruned to the current install. pnpm/setup's `cache: true` saved a ~290 MB store from every job under that job's own key: on 2026-10-22, 33 of those filled 10 GB of the repo's 10.54 GB cache, over GitHub's 10 GB limit, and pushed out the turbo caches that let unchanged packages skip their tasks.
- **Don't order one package's tests after another's with turbo's `dependsOn`.** Turbo runs a filtered task's dependencies unless `--only` is passed, so CI's docs job (`--filter=@oakoss/docs`) would run the Storybook suite too, and `--only` would skip the docs build that job needs. Turbo has no per-task concurrency, only a global `--concurrency`, which would make the unit suites wait as well; instead, Storybook's worker cap leaves the docs suite room to run alongside it.
- **The docs build prerenders one page at a time** (`prerender.concurrency: 1` in `apps/docs/vite.config.ts`). TanStack Start's default, one request per core, fetches from a preview server in the same process, and on a busy machine the build failed with `fetch failed` (undici's 10s connect timeout). Measured on a 12-core Mac: the default failed 2 of 9 builds (one under 36 `yes` CPU hogs, one just after), both in the first batch of requests; 1, 2 and 4 failed none of 11 between them (7 under the same load); unloaded, each prerendered 710 pages in 19s. The likely cause, inferred rather than measured: the first cold render blocks the shared event loop while the other requests wait to connect. Its `retryCount` can't paper over this: a retried page is skipped as already seen.
- **Docs e2e tests open pages with `gotoHydrated`** (`apps/docs/e2e/hydrated.ts`) before clicking or typing. The prerendered page shows before React hydrates it, and input in between is lost; on CI that dropped a demo click and a tab choice. A plain `goto` waits only for the preloaded scripts, not the page's own MDX chunk.
- **Test that requests go out together by holding their responses,** as the Manual tab's test does with `page.route`: a waterfall stalls at the first request, however slow the runner, where a timing check flakes. Don't assert that no request starts after another finishes: the e2e server speaks HTTP/1.1, so Chromium queues past six connections even when every request is made at once. Source chunks are named `source-<file>-<hash>.js` (`lazy-sources-plugin.ts`), so the test counts a tab's own files exactly, not a component's runtime chunk of the same name; `bundle.test.ts` checks the naming holds.
- **Test `:active` styles with `whilePressed`** (`apps/storybook/src/helpers/press.ts`), which holds a real mouse down through Vitest's browser `userEvent` and reads the element mid-hold. Storybook's `userEvent` dispatches synthetic events, which never trigger CSS `:active`, so a story pressing a plain link with it passed with the `joined` recipe's press rule removed. Assert that the element matches `:active` too, so a press that never landed can't pass. React Aria elements take `pressed:` from `data-pressed`, which a story can set directly.
- **Hover a plain element (no `data-rac`) with `hoverReal`** (`apps/storybook/src/helpers/pointer.ts`), which moves the real mouse through Vitest's browser `userEvent`. `hover:` matches only `:hover` there, so setting `data-hovered` checks nothing: Badge's static-hover story did that and passed with a hover fill added. Assert the element doesn't match `:hover` before the resting read and does after hovering, so a leftover or missed hover can't pass.
- **A popup's trigger story checks that the trigger's `aria-controls` names the popup, and where focus goes on close,** as Select's and DropdownMenu's do (Combobox keeps focus in its input). Finding the list with `findByRole` proves a popup exists, not that our wrapper kept the trigger linked to it. These were the checks `@react-aria/test-utils` makes that our stories lacked; they cover the rest, and its testers can't drive ContextMenu, inline Command or our plain Table, so we don't use it.
- **Behavior a component adds on top of React Aria gets a keyboard story where the keyboard reaches it,** as Combobox's decoration buttons do, but no touch story. React Aria sends a touch press and an outside press through the same handlers as a mouse click, so every tap story we tried failed only where its click story already did. Write one only for code that reads `pointerType` or otherwise treats touch differently, with Storybook's `userEvent.pointer({ keys: '[TouchA]' })`, which fires pointer events with `pointerType: "touch"`, then mouse events and a click, but no touch events.
- **Check that a browser-internal pseudo-element is hidden with `isPseudoHidden`** (`apps/storybook/src/helpers/pseudo.ts`), which looks for a loaded rule that sets `display: none` on it, matches the element and sits under media and supports conditions that hold. It doesn't resolve the cascade, so it proves the rule applies, not that nothing later overrides it. Chromium's `getComputedStyle(input, '::-webkit-search-cancel-button')` returns the input's own style, so a check through it read `block` with the rule in place.
- **Links a story clicks have no `href`.** Clicking a link with an `href`, even `#home`, navigated the test page and closed Vitest's browser connection (`VITEST_BROWSER_CONNECTION_CLOSED`). React Aria's `Link` stays focusable and pressable without one, so press handlers and pointer focus still test.
- **Stories that show today freeze the clock with `freezeDate`** (`apps/storybook/src/helpers/date.ts`) in `beforeEach`, so a check on today's mark or the month on screen doesn't change from one day to the next. It replaces `Date.now`, the only clock `@internationalized/date` reads; a spy on it recursed, since the test runner reads `Date.now` too.
- **Check styles under a media condition that doesn't hold with `valueUnderMedia`** (`apps/storybook/src/helpers/media.ts`), which reads the value a loaded rule gives the element there, such as Calendar's 44px days under `any-pointer: coarse`. Don't emulate the media through the DevTools protocol: CI runs every story file in one page, and after a story turned on touch emulation the stories that followed lost their hover styles, though it was turned off again.
- **Check phone-width layout with `atViewportWidth`** (`apps/storybook/src/helpers/viewport.ts`), which resizes the viewport for one check and restores it. Stories run at 1200px, where every `sm:` style applies, so Breadcrumb's narrow-screen gap went unchecked until its spacing story ran at 375px. Close any overlay before the check returns, and blur a control that shows a tooltip on focus once focus has returned to it: the Visual capture runs after the width is restored, and React Aria positioned an open tooltip before the desktop layout moved its trigger, leaving it where the trigger had been. A story that should be captured at phone width uses `beforeEach: phoneWidth` instead.
- **A story that checks a click is left alone uses a control React Aria doesn't handle.** React Aria's `Button` cancels its own click, so a handler further up never acts on it, and a story clicking a Button passes whether or not that handler's own skip rule works. InputGroup's addon-click story passed with the interactive-target check removed until it clicked a native `<select>` and a custom `role="switch"` instead.
- **One press per element.** Storybook's `userEvent` releases a held press without React Aria seeing it, so a second reading on the same element sees a stale `data-pressed`.
